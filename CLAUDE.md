# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

blockout is a Go CLI that turns a YAML layout of boxes into a game-asset sheet generated by Nano Banana (via OpenRouter Chat Completions). It cuts every box out as its own transparent PNG and writes a `manifest.json` that an engine can load. Its primary user is an agent: every command prints one JSON object on stdout, writes files to disk and never prompts.

Read `EXPERIMENTS.md` before changing behaviour. It is the lab notebook (E1–E10) and explains why each current default exists, with run ids, scores and decisions.

## Commands

```sh
go build -o blockout.exe ./cmd/blockout   # binary is gitignored
go test ./...
go test ./internal/matte -run TestName    # single test
go vet ./...
```

CLI (`go run ./cmd/blockout help` gives the full usage):

```sh
blockout sketch <layout.yaml>                   # validate + draw sketch; free
blockout gen <layout.yaml> --backend fake       # whole pipeline, free
blockout gen <layout.yaml> --dry-run            # writes request.json, no call, free
blockout gen <layout.yaml> --tag e11 --budget 0.50  # PAID: needs OPENROUTER_API_KEY
blockout extract <run-dir> [--matte soft|hard]      # re-derive everything from a stored sheet; free
blockout runs [--tag t] [--name n]              # list runs, cost and scores, grouped by variant
blockout export <run-dir>... --to <dir> [--js NAME]  # pieces of several runs + one manifest.json (and manifest.js); iso sprites carry their run's tile; free
```

Run directories are created under `--out` (default `out/`, relative to the CWD) as `<name>-NNNN`. `<name>` is the parent directory for a file named `layout.yaml` (`examples/ui-kit/layout.yaml` → `ui-kit`); for any other file it is `<dir>-<stem>` (`art/ui.yaml` → `art-ui`).

Exit codes have fixed meanings and are tested: 0 ok, 1 internal, 2 usage, 3 layout invalid (with line-numbered `problems`), 4 model call failed (`error.retryable`), 5 missing API key, 6 tag budget reached.

## Architecture

The pipeline in `cmd/blockout/gen.go` runs one stage per `internal/` package:

1. **layout**: parses and validates YAML with line-numbered problems (goccy/go-yaml AST). **All coordinates are pixels of the 1K image at the canvas aspect** (e.g. 1024×1024 for 1:1, 1376×768 for 16:9). Downstream code scales them to whatever size the model returned, so one layout serves 1K/2K/4K. `grid` + `cell` fill in boxes. `footprint`/`pivot`/`iso` drive the isometric path. A layout with a `prompt` and no `pieces` is a *reference* layout: it makes one style-ref image, and nothing gets extracted.
2. **sketch**: the annotation image sent to the model. Its style is `colors` (default since E3: each box filled with a nameable colour, "in the red box, draw …"), `blocks`, `outlines` or `none`. `colors` caps the piece count by the number of colours distinct from the key, and `gen`/`sketch` refuse layouts that exceed it. Iso layouts draw white footprint diamonds.
3. **prompt**: compiles the layout into interleaved text/image parts (intro, sketch, each style ref introduced by name, one line per piece). Everything derives from the layout file.
4. **backend**: the `Backend` interface with `OpenRouter` and `Fake`. `Fake` turns sketch blocks (or iso diamonds) into shaded shapes with drift, so everything except the paid call can be tested. The stored request/response JSON has image data replaced by a `<elided label: N bytes, sha256 …>` placeholder.
5. **derive** (`gen.go`, shared by `gen` and `extract`): everything computed from a sheet without the model.
   - `segment.Run` is the single source of truth for scoring and extraction. Pixels far from the key colour count as drawn. They form 8-connected regions, and each region goes to the box holding most of its pixels. Pieces are found as drawn regions, not by cropping boxes, because the model consistently overgrows boxes by about 25% (E2).
   - `measure.Score` writes `scores.json`: per-piece spill, IoU, size ratio and leak; per-sheet background noise.
   - `matte.Compute` writes `sheet_alpha.png`. Background is the near-key area connected to the border, plus enclosed holes that pass the size/thickness rules. `soft` (default) adds partial alpha on edges, key unmixing and a classic despill.
   - `extract.Run` cuts each piece from the pixels it owns and trims it, so a piece file can never contain a neighbour. The trim ignores alpha below 4 and drops faint edge strips (never reaching alpha 32) that an empty row or column cuts off from the art (E10). It flags `missing`, `touches_edge`, `merged:<id>`, `intrudes:<id>`, `key_inside` and `key_cast` (the body tinted toward a coloured key).
   - `extract.UI` (with `internal/ui`) finds nine-slice insets for `nine_slice` and `button` pieces from flat row/column runs. `slice` is what must not stretch. `content` is the rim's thickness, where an engine puts contents. The two differ when a one-off mark (a glare) sits on one edge. It groups button states by id suffix (`btn_x_pressed` is a state of `btn_x` when the boxes are the same size), aligns them and pads them onto one shared canvas.
   - `extract.Sprites` (with `internal/iso`) detects each iso sprite's base (corner or round), then corrects its scale to the layout tile, squashes it toward 2:1 and sets the pivot on the footprint's front corner. It re-measures after correcting. Pieces that fail the detection gates fall back to sheet medians and are flagged `unmeasured`/`scale_estimated`.
   - `preview` renders `preview.png` (sketch | sheet with boxes and drawn bounds | pieces on a checkerboard, plus a UI strip). For iso sheets it also renders `scene.png`, with the sprites stood on a tile grid.

A run directory holds `run.json` (status, model, provider, cost, attempts, sketch style, tag), plus `layout.yaml`, `sketch.png`, `prompt.txt`, `request.json`, `response.json`, `sheet.png`, the derived files and a `refs/` copy of every style ref used. `extract` reads the sketch style from `run.json`, so stored sheets re-extract the same way they were generated. `runs` and the `--budget` check both work by scanning `run.json` files under `--out`.

## Working rules

- **Free before paid.** Use `--backend fake`, `--dry-run` and `extract` on stored sheets for anything that doesn't need a new image. Paid runs must use `--tag` with a `--budget`. Ask the user before raising a budget (exit 6 says so). Use the cheapest settings (1K) for layout questions.
- **Defaults change only when an `EXPERIMENTS.md` entry backs them.** Add a new entry for each experiment: question, variants, run ids, scores, decision. Run each variant 2–3 times, since outputs vary.
- **Code does what code can.** Size, alpha, insets, scale, angle and pivots are fixed in post-processing, not by prompting. E7/E8 showed that boxes and guides don't control scale.
- **Small surface.** Add a command, flag or layout field only when an experiment shows it is needed. Button states, for example, use an id convention rather than a new field.
- **Taste calls go to the user.** When the deciding factor is how something looks, show the candidates (preview/contact images) rather than choosing.
- `skill/blockout/` is the Claude Code skill that teaches an agent to use blockout (SKILL.md plus `references/`). When a change alters something the skill describes (a flag, a manifest field, a lesson), update the skill too (E10).
- `examples/` holds starter layouts for the README. They must keep passing `blockout sketch`.

## OpenRouter facts learned the hard way

- `400 "Request path cannot be relayed"` is a DNS issue at the edge, not a problem with the request. Changing the body, model, provider pin or ref size won't fix it. It hit 25–75% of requests in E1 and none in E2. blockout retries it like a 502, up to 8 attempts. Other 400s fail immediately. Failed generations are not billed.
- The default model is `google/gemini-nano-banana-2.1`. `google/gemini-3.1-flash-lite-image` (2 Lite) behaves differently: it leaks sketch marks, draws literal 3×3 panels and has a noisy background. It is not a cheap stand-in for 2.1 in experiments.
- `#00FF00` with the soft matte is the default key. Black keys are flatter but eat dark outer outlines, so they are only OK for UI with light rims.
